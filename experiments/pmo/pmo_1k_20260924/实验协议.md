## 预算与指标

每个方法、目标、随机种子各 1,000 次独立有效分子 oracle 评分；规范化去重、重复命中缓存、无效 SMILES 返回零且不增加有效查询数，均遵循 PMO 原评分入口。所有生成、初始化和内部反馈的真实目标评分均经同一台账；不允许预算外筛选。

严格在 1,000 处停止，修正原入口 `>` 的越界边界；批量候选按原始顺序计费，到预算即停止，不在全批评分后反向择优。

主指标直接抽取 PMO `main/optimizer.py::top_auc`，freq_log=100（原仓库默认），并同时保存 freq_log=1 的密集曲线 AUC。二者不能混报，MT-Mol 自己的生成序号式 AUC 不冒充原 PMO 唯一分子查询口径。保存每个查询的顺序、SMILES、分数和来源，可重算。

2026-09-25 按用户要求，当前只运行种子 [0]，4×23=92 个独立搜索，最多 92,000 次计费 oracle 评分。其余种子不投递。原初始化文件保留，仅使用 seed 0，避免重写已运行实验的输入哈希。4 个并行进程。API 次数、token、截断和耗时另记；本协议不声称 LLM token 预算相同。

## 共同搜索外层：明确属于本次接入选择

三个原 agent 都是分子编辑入口，没有完整 PMO 搜索外层。四组统一采用以下外层，不声称是作者原版 PMO 实验：

1. 从已有 ZINC250K CSV 仅取 SMILES，忽略原有 logP/QED/SAS 列。按种子随机选择 100 个不同有效分子，不进行目标得分筛选。
2. 同种子四组使用完全相同的这 100 个初始分子，它们消耗各自 1,000 预算中的前 100 次。其余 900 次供搜索。该初始化大小是本次实验配置，不是 PMO 强制规定。
3. 每次编辑从当前已评分档案的前 100 名中均匀抽取一个父分子，排序用得分与初次出现顺序，随机选择由种子和 episode 编号确定。
4. 四组都获得相同的目标描述、所选父分子，以及最近 20 个已评估结构以减少重复；直接模型没有内部评分反馈、检索或多轮纠错，但同样使用这个公共父分子选择外层。因此应标为“DeepSeek 直接生成 + 公共搜索外层”，不是完全无搜索的零样本单次调用。
5. ChatDrug/AgentDrug 的参考集合改为已计费的档案，每次 episode 开始时冻结。没有免费预评分的 10,000 分子库，也没有 MT-Mol Top-100 检索数据。

## 三个 agent 的保留项与接入修改

- ChatDrug：执行原 `conversation`、`ReDF`、`retrieve_and_feedback` 和原解析函数。两轮反馈、最多三次生成；原解析器仅取第一个符合格式的分子这一行为保留，不额外评分文本中的其他分子。PMO 分数严格高于父分子作为该次编辑的 hit。相似度检索流程保留，检索档案范围变更见上。
- AgentDrug：使用此前核验的 `core_fixed.py`，新增 `PMO+` 通用性质分支替换具体描述符。保留有效性反馈、分数反馈、相似参考分子检索和最多四次生成。保留作者原来的 max_completion_length=256；这不是本次新增上限。所有生成候选（包括最后一次）均计入 PMO 台账。
- MolLingo：直接复用此前核心入口，任务说明替换为 PMO 目标；原三项片段修改、笛卡尔积重组、原始枚举顺序全部保留。取消单分子选择步骤；每个新有效候选都按次评分。保留原输入/无修改重组产物，按 PMO 的规范化缓存规则处理。保留此前已披露的解析/兼容修复，不修正原重组语义。
- 除 AgentDrug 原始 256 输出上限外，其他方法不额外设 max_tokens。

## 验证、恢复与操作防护

正式启动前：23 个 oracle 各对三种合法结构数值检查；预算去重、无效输入、严格边界和断点恢复测试；官方 AUC 常数序列数值核验；四组 × QED/DRD2/Amlodipine 三个目标各 110 次预算冒烟测试（100 初始化 + 10 新评分），冒烟结果不并入正式数据。

台账逐行 fsync，API 请求和响应按请求内容缓存，episode 父分子与档案边界持久化，支持原路径断点续跑。

2026-09-25 按用户要求删除“连续 100 个 episode 无新增分子即停止”规则。原 stalled 搜索由现有台账与 episode 状态继续，不清空、不增加分数，也不将重复结构计为新 oracle 调用。

超长截断定义为 API 返回 finish_reason=length 且请求未显式设置 max_tokens，即触及服务端默认输出上限；AgentDrug 作者设置的 256-token 短截断不计入。每个方法×目标×seed 累计 3 次此类独立响应后标记 skipped_long_truncation，保留已有轨迹并进入下一任务，不算跑满预算。既有 API 日志中的此类响应计入累计，同一缓存响应重放不重复计数。截断文本在返回 agent 的解析器之前被拦截，不送入 RDKit 或评分器。达到 3 次前，记录该 episode 的失败并继续下一 episode。

使用每次最多 100 个 episode 的轮换调度；这只是让出执行槽位，未完成搜索自动排回队尾继续，不产生终止结果。这样低新增率任务不会长期挡住其他 23 个目标。真正的 API/程序错误仍独立记录，三个进程错误后停止继续投递以便排查。

修改前已 complete 的结果保留原配置与轨迹，不回溯改变完成状态。修改前代码、配置、台账快照位于服务器 policy_backup_20260925；每个恢复任务另有 config_history/result_history。新代码只允许源代码哈希和运行策略字段迁移，模型、目标、初始化和预算等字段必须保持一致。

不修改或停止 MolClaw 的运行。
